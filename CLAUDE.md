# CLAUDE.md

## Project

Customer-facing Terraform provider (`terraform-provider-pantechdynamics`) for our cloud platform, which runs on Apache platform.

Paying customers write Terraform to create resources on their own account.

```
terraform apply -> this provider (Go) -> our backend REST API -> platform
```

- The provider talks ONLY to our backend API. It never imports or calls platform.
- The backend is the source of truth for auth, quotas, billing and IPs. The provider is a thin, typed translation layer.
- Customers see our concepts (plans, images, regions), never platform concepts (service offerings, templates, zones).

## How we work (read first)

The owner is learning while building. Code must be readable by a developer who knows Java/Spring Boot but is new to Go and to Terraform providers.

1. **Small steps.** One resource or one concern at a time. Never generate a whole provider in one go.
2. **Explain before code.** Before writing, state in 2-4 lines what you will add and why. After writing, give a short trace of what happens at runtime (for example: "`terraform apply` -> Create -> POST -> id saved to state").
3. **Teach Go idioms when they first appear.** One or two lines, using a Java analogy where it helps (interface vs Java interface, `error` returns vs exceptions, `context.Context`, struct tags).
4. **Terse.** Short confirmations, no lengthy discussion. Ask at most one question at a time, and only when blocked.
5. **No silent decisions.** If there is a design choice (naming, schema shape, retry policy), name the options in one line each, recommend one, and wait for approval.
6. **Verify, don't claim.** After each step, run the build, lint and tests, and report the real output. Never say something works without running it.
7. **Push back.** If a request conflicts with this file or with Terraform conventions, say so and explain why.

## Stack

- Go 1.27+
- `terraform-plugin-framework` (NOT the legacy SDKv2)
- `terraform-plugin-testing` for acceptance tests
- `terraform-plugin-docs` (`tfplugindocs`) for generated docs
- `golangci-lint` for linting
- `goreleaser` for releases (signed, registry-compatible)
- Standard library `net/http` for the API client. No heavy HTTP frameworks.

## Architecture

```
.
├── main.go                      # provider server entrypoint only
├── internal/
│   ├── client/                  # our API client. No Terraform imports here.
│   │   ├── client.go            # HTTP plumbing, auth, error mapping
│   │   ├── errors.go            # ErrNotFound, APIError, etc.
│   │   ├── sshkey.go            # one file per API resource
│   │   └── *_test.go            # httptest-based unit tests
│   ├── provider/
│   │   └── provider.go          # provider schema, configure, resource/datasource registry
│   ├── resources/               # one package or file group per resource
│   │   └── sshkey/
│   │       ├── resource.go      # schema + CRUD
│   │       ├── model.go         # tfsdk model structs
│   │       └── resource_test.go # acceptance tests
│   └── datasources/             # plans, images, regions
├── examples/                    # runnable HCL, used by docs
├── docs/                        # GENERATED by tfplugindocs. Never hand-edit.
└── .goreleaser.yml
```

### Layer rules

- `internal/client` knows nothing about Terraform. It takes and returns plain Go structs.
- `resources/*` knows nothing about HTTP. It calls the client through an **interface** defined in the consuming package, so it can be faked in tests.
- `provider.go` only wires things together: reads config, builds the client, registers resources.
- Mapping between Terraform models and API structs lives in small, named functions (`toAPIRequest`, `fromAPIResponse`). No inline mapping inside CRUD methods.

## Code standards

### General
- Idiomatic, boring Go. Clarity over cleverness. No premature abstraction or generics.
- Small functions with one job. If a function needs a comment to explain its sections, split it.
- Comments explain WHY, not what. Every exported identifier has a doc comment.
- No global mutable state. No `init()` side effects. Dependencies passed explicitly.
- Wrap errors with context: `fmt.Errorf("creating ssh key: %w", err)`. Use `errors.Is` / `errors.As`.
- Pass `context.Context` as the first parameter through every call that does I/O. Respect cancellation and timeouts.
- Never log secrets (API tokens, private data). Use `tflog` for provider logging, never `fmt.Println`.

### Client
- Typed request and response structs with JSON tags. No `map[string]any` for known shapes.
- Map HTTP status to typed errors in one place (404 -> `ErrNotFound`, 401/403 -> auth error, 429 -> rate limited, 4xx -> `APIError` carrying the backend message).
- Client has a configurable base URL, timeout and user agent (`terraform-provider-pantechdynamics/<version>`).
- Retries only for safe cases (idempotent GETs, 429, 5xx) with backoff. Never blindly retry POST.
- Async operations: poll a `status` field with a context-aware loop and a timeout. Put the polling helper in one place.

### Resources
- Every resource implements Create, Read, Update, Delete and ImportState.
- **Read is the source of truth.** If the API returns `ErrNotFound`, remove the resource from state (`resp.State.RemoveResource(ctx)`), do not error.
- Immutable fields use `RequiresReplace` plan modifiers. Do not fake in-place updates.
- Computed fields use `UseStateForUnknown` where appropriate to avoid noisy diffs.
- Mark secrets `Sensitive: true`.
- Add validators for inputs the backend would reject anyway (names, CIDRs, enums), so users get errors at plan time.
- Create must be safe on partial failure: if the API call succeeded but the follow-up failed, state must still be saved when possible.
- Every attribute has a `Description` (used by generated docs).
- Support `timeouts` blocks on resources that poll.

### Naming
- Resources: `pantechdynamics_<noun>` singular, snake_case (`pantechdynamics_ssh_key`, `pantechdynamics_instance`).
- Attributes match the backend API field names unless the backend naming is bad for users. Flag the mismatch instead of silently renaming.

## Testing

- **Client:** unit tests with `httptest.Server`. Cover success, 404, 401, 429, 5xx and malformed JSON. Table-driven.
- **Resources:** acceptance tests with `terraform-plugin-testing` (`resource.Test`). Required cases: create, read-back, update or replace, import, destroy, and drift (resource deleted outside Terraform).
- Acceptance tests run only with `TF_ACC=1` against the test zone, never against production.
- A resource is not done until its acceptance tests pass.

## Commands

```bash
go build ./...                      # must pass
go vet ./...
golangci-lint run                   # must pass, no new warnings
go test ./...                       # unit tests
TF_ACC=1 go test ./... -v           # acceptance tests (test zone only)
go generate ./...                   # regenerate docs via tfplugindocs
```

Local manual testing: build the binary and point `~/.terraformrc` `dev_overrides` at it. Run `terraform plan` and `apply` against `examples/`.

## Definition of done (per resource)

1. Client methods and unit tests
2. Resource with full CRUD plus import
3. Validators and plan modifiers
4. Acceptance tests passing (including drift)
5. Example in `examples/`, docs regenerated
6. Lint and build clean
7. Short runtime trace explained to the owner

## Backend API contract

> Keep this current. Claude must treat it as the source of truth and ask before assuming anything not listed here.
> Items marked **(verified)** were tested against the dev host on 2026-10-03. Items marked **(unverified)** come from the OpenAPI spec or backend code only.

- **Base URL:** the prefix differs per environment, so `base_url` must be a provider setting (default from env var), never hardcoded. **(verified)**
  - dev: `https://api-dev.pantechdynamics.com/public/v1`
  - prod: `https://api.pantechdynamics.com/v1`
  - A wrong prefix returns `404` with `code: GATEWAY_NO_ROUTE`. That is a configuration error, not a missing resource.
  - Spec file: `cloud/contracts/openapi/control-api.yaml`. Its short-path section ("API key only") is what this provider uses.
- **Auth:** `Authorization: Bearer PAN_...` (an API key, created by an owner or admin in the console). **(verified)**
  - Keys are per environment. A dev key gets `401` on prod.
  - Scopes: `read` or `write` (`write` includes `read`). A read-only key cannot create or delete. **(unverified)**
  - A key cannot manage API keys. The provider never needs to.
  - Never log the key. Mark the provider's `api_key` attribute `Sensitive`.
- **Idempotency:** every POST, PUT and DELETE requires an `Idempotency-Key` header, or the API returns `400 IDEMPOTENCY_KEY_REQUIRED`. This applies even to DELETE of ids that do not exist. **(verified)**
  - Send a new UUID per logical operation. Reuse the same key only when retrying that same request.
- **Error format:** `application/problem+json`. **(verified)**
  ```json
  {"type":"https://api.pantechdynamics.com/problems/resource-not-found","title":"Resource not found","status":404,"code":"RESOURCE_NOT_FOUND","detail":"No resource matches this request.","request_id":"req_..."}
  ```
  - Branch on `code`, not only on `status`. Include `request_id` in error diagnostics so support can find the request.
  - Codes seen: `RESOURCE_NOT_FOUND` (404), `GATEWAY_NO_ROUTE` (404), `UNAUTHENTICATED` (401), `IDEMPOTENCY_KEY_REQUIRED` (400).
  - Codes from the spec, not yet seen: `API_KEY_NOT_ALLOWED` (403), `FORBIDDEN` (403), `RATE_LIMITED` (429), 409 for a duplicate ssh key name or fingerprint, 422 validation failures. **(unverified)**
- **Not found:** a missing resource returns `404 RESOURCE_NOT_FOUND`. **(verified)** This includes a GET or DELETE of a deleted id, a well-formed id that never existed, and a malformed id.
  - Read: remove from state. Delete: treat as success, because a second DELETE returns 404, not 204.
- **Rate limit:** 120 requests per minute per key, returning `429` with `Retry-After`. **(unverified, from backend code)** Back off on 429 and avoid parallel refresh storms.
- **Latency:** typical calls take about 0.5 to 0.9 seconds. One call took about 15 seconds. Use a client timeout of 60 seconds or more. **(verified)**
- **Pagination:** list endpoints are cursor-based (`next_cursor`). The ssh-key list returns `{"data":[...]}`. **(verified for ssh-keys, unverified for the rest)** Follow the cursor until it is empty.
- **Async behavior:** **(unverified, not yet tested)** creating an instance returns an order, polled with `GET /instance-orders/{order_id}`. Other long operations are polled with `GET /operations/{operation_id}`. Terminal states are not yet documented. Test with a throwaway resource and fill this in before building `instance`.

| Resource | Create | Read | List | Delete | Notes |
|---|---|---|---|---|---|
| ssh-key | `POST /ssh-keys` | `GET /ssh-keys/{id}` | `GET /ssh-keys` | `DELETE /ssh-keys/{id}` | See below. All **(verified)**. |

Paths above are relative to the base URL.

**ssh-key details** **(verified)**
- Create body: `{"name": "...", "public_key": "ssh-ed25519 AAAA..."}`. Returns `201` with `id` (`sshk_...`), `name`, `fingerprint`, `public_key`, `created_at`.
- `public_key` is optional. If omitted, the backend generates a keypair and the response also carries a one-time `private_key`. It cannot be retrieved again, so it must be saved to state as `Sensitive` at create time.
- Delete returns `204` with no body.
- There is no update endpoint, so `name` and `public_key` use `RequiresReplace`.
- A name or fingerprint already registered returns `409`. **(unverified)**
- Backend IDs are prefixed (`sshk_`, `key_`, ...). Validate the prefix in import, so a wrong id fails at plan time.

## Build order

1. Client plus `pantechdynamics_ssh_key` (proves the whole pipeline end to end)
2. Data sources: `plans`, `images`, `regions`
3. `pantechdynamics_firewall`
4. `pantechdynamics_instance` (async, polling)
5. Volumes, IPs, VPCs
6. Registry publishing

## Do not

- Use SDKv2 or copy patterns from old blog posts that use it.
- Call platform directly or expose platform terms in the schema.
- Hand-edit `docs/`.
- Add dependencies without stating why and getting approval.
- Generate multiple resources at once or skip tests to move faster.
- Commit secrets, tokens, or real customer data. Use env vars (`PANTECHDYNAMICS_API_KEY`).
