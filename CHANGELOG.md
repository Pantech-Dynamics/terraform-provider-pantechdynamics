# Changelog

## 0.2.0 (2026-10-08)

FEATURES:

- `pantechdynamics_public_ip`: `instance_id` is now optional for `static_nat` and changes in place. Leave it out to reserve an address without an instance; change it to move the same address to another instance (`POST /public-ips/{id}/attach`); remove it to detach the address and keep it (`POST /public-ips/{id}/detach`). The address and its id never change, and it is billed once while held, attached or not. The update waits for the operation (skipped when the API answers an empty `operation_id` because nothing changed), then until the address is in sync and points at the planned instance. New read-only `in_sync`, false while an attach or detach is applying, and an `update` timeout. `port_forwarding` and `load_balancer` addresses still refuse `instance_id` at plan time. `INSTANCE_ALREADY_HAS_PUBLIC_IP` (on create and attach), `PUBLIC_IP_NOT_STATIC_NAT` and `INVALID_RESOURCE_STATE` come with a hint, and `INSTANCE_NOT_IN_NETWORK` points at `instance_id`.
- `pantechdynamics_instance`: a delete refused with `INSTANCE_HAS_PUBLIC_IP` now says to detach the address (remove `instance_id` from the `pantechdynamics_public_ip`, keeping it) or release it.
- **New resource:** `pantechdynamics_load_balancer`, which spreads one TCP port of a `load_balancer` public IP across instances in one subnet of a VPC network. `name`, `algorithm` (`roundrobin`, `leastconn` or `source`) and the targets (`instance_ids`, the whole set) change in place with one `PATCH`; `public_ip_id`, `subnet_id`, `public_port`, `private_port` (defaults to `public_port`) and `cidr_list` (at most 20 IPv4 CIDRs, empty for any source) replace it. Create and update wait until the load balancer is active and every target change is applied. At most 50 targets. Supports import by id and `timeouts` (create, update, delete). `PUBLIC_IP_NOT_FOR_LOAD_BALANCER`, `PORT_IN_USE` and `LOAD_BALANCER_NOT_CHANGEABLE` refusals come with a hint.
- **New data source:** `pantechdynamics_load_balancer`, an id-or-name lookup of an existing load balancer.
- `pantechdynamics_public_ip`: `purpose` accepts `load_balancer` (no `instance_id`). Releasing an address that still carries load balancers (`PUBLIC_IP_HAS_LOAD_BALANCERS`) says to delete them first.
- `pantechdynamics_instance`: a delete refused with `INSTANCE_BEHIND_LOAD_BALANCER` says to remove the instance from its load balancers first.
- **New resource:** `pantechdynamics_kubernetes_cluster`, a managed Kubernetes cluster whose nodes are VMs of `node_plan` in your account. `workers` (1 to 10) changes in place by scaling, and `kubernetes_version_id` changes in place by upgrading to one of `available_upgrade_ids` (checked at plan time; never down). `name`, `zone_id`, `subnet_id`, `node_plan` and `control_nodes` (1, or 3 where offered) replace it. Create and update wait until the cluster is running and in sync; the admin kubeconfig is downloaded into the sensitive `kube_config` once it runs, and on a refresh only when the state holds none. Destroy stops the cluster at once; the platform destroys its nodes and volumes 12 hours later. Supports import by id and `timeouts` (create 60m, update 60m, delete 20m). `KUBERNETES_*` refusals and `INSUFFICIENT_CREDIT` come with a hint.
- `pantechdynamics_kubernetes_cluster`: new optional `autoscaling` (`enabled`, `min_workers` and `max_workers`, 1 to 10) turns on the cluster autoscaler, which moves the worker count within the range; credit and account limits are checked for `max_workers`, and the cluster starts at `min_workers`. Set either `workers` or an enabled `autoscaling`, not both: `workers` is now optional and computed, required (checked at plan time) only while autoscaling is off, and refused at plan time while it is on, because the autoscaler owns the count. The count the autoscaler chooses is read back into `workers` and never causes a diff; a plan that changes the cluster shows it as known after apply. Turning autoscaling off (removing it, or `enabled = false`) needs `workers` set, and is sent with it in one request.
- `pantechdynamics_kubernetes_cluster`: new optional `api_allowed_cidrs`, a set of at most 20 IPv4 CIDRs allowed to reach the API server (VPC zone only, so it needs `subnet_id`; both checked at plan time). Empty, the default, allows any address; removing it sends `[]`.
- `pantechdynamics_kubernetes_cluster`: `workers`, `autoscaling` and `api_allowed_cidrs` now change in place with one `PATCH` carrying only what changed (a version upgrade is still its own request, sent first), and the update waits until the cluster is running and in sync. New read-only `endpoint` (the API server URL, null until there is one) and `volume_storage_gb` (storage the workloads' persistent volume claims use, billed with the nodes' disks).
- `pantechdynamics_kubernetes_cluster`: `INVALID_KUBERNETES_AUTOSCALING`, `INVALID_API_ALLOWED_CIDRS` and `API_ALLOWED_CIDRS_VPC_ONLY` point at their attribute with a hint, and a create or scale that fails with `PROVISIONING_LIMIT_EXCEEDED` says which nodes count against the account limits (control nodes plus workers, or plus `max_workers`).
- `pantechdynamics_kubernetes_cluster` data source: new read-only `autoscaling`, `api_allowed_cidrs`, `endpoint` and `volume_storage_gb`.
- `pantechdynamics_public_ip`: a create refused with `PUBLIC_IP_LIMIT_EXCEEDED` (20 public IPs of any purpose per organization by default) or `STATIC_NAT_LIMIT_EXCEEDED` says to release an address or ask support to raise the limit.
- A deleted managed database that answers `404 DATABASE_NOT_FOUND` now counts as gone: a refresh removes it from state and a destroy finishes, instead of failing. The same holds for every other resource-specific 404 code in the API (`DATABASE_SNAPSHOT_NOT_FOUND`, `DATABASE_ORDER_NOT_FOUND`, `RECEIPT_NOT_FOUND`, alongside `RESOURCE_NOT_FOUND` and `SNAPSHOT_SCHEDULE_NOT_FOUND`).
- A Kubernetes cluster that answers `404 KUBERNETES_CLUSTER_NOT_FOUND`, as a deleted one does during its 12-hour retire window, now counts as gone: a refresh removes it from state and a destroy finishes at once, instead of failing.
- **New data source:** `pantechdynamics_kubernetes_versions`, the versions offered for new clusters (optionally in one `zone_id`) and the zones offering 3 control nodes (`ha_zone_ids`).
- **New data source:** `pantechdynamics_kubernetes_cluster`, an id-or-name lookup of an existing cluster's metadata. It does not expose the kubeconfig.
- `pantechdynamics_subnet`: a delete refused with `SUBNET_HAS_KUBERNETES_CLUSTERS` says to delete the clusters in it first.

## 0.1.0 (2026-10-07)

FEATURES:

- **New resource:** `pantechdynamics_database`, a managed PostgreSQL, MySQL or MariaDB database. Create pays for the order first and then waits for provisioning, like an instance. Access rules (the whole CIDR allow-list), attached security groups (`security_group_ids`, with the read-only `effective_access_rules` and `ignored_security_group_rules`) and the power state (`desired_state`) change in place. The admin password is the write-only argument `password_wo` (Terraform 1.11 or later), so it is never stored in plan or state; changing `password_wo_version` sets a new one. Supports import and `timeouts`.
- **New resource:** `pantechdynamics_database_snapshot`, a crash-consistent snapshot of a managed database's data disk. It is created and deleted (any change replaces it), waits for the snapshot to become active, and is imported as `<database_id>/<snapshot_id>`. It outlives its database and stays billed until deleted.
- `pantechdynamics_database`: new `storage_gb` (optional, computed) sets the data disk size at create; increasing it grows the disk in place (`POST /databases/{id}/resize-storage`, online, starting a stopped database for it and stopping it again). A smaller value is an error at plan time, and never replaces the database. A resize in flight is reported as its target size and waited for instead of being sent again.
- `pantechdynamics_instance`: new `private_network` (optional, computed bool) attaches or detaches the interface on the zone's private database network in place, and the read-only `private_network_ip` is its address, to allow on a database as a `/32`. When the security group lets in the private range the API's `SECURITY_GROUP_ALLOWS_PRIVATE_NETWORK` message, which names the rules to narrow, is shown with a hint, on `private_network` for an attach and on `security_group_id` for a group change. It is refused at plan time on an instance in a subnet.
- **New data sources:** `pantechdynamics_database_engines` (engines, version lines and their zones), and the id-or-name lookups `pantechdynamics_security_group`, `pantechdynamics_ssh_key`, `pantechdynamics_instance` and `pantechdynamics_network`.
- `pantechdynamics_public_ip`: new read-only `network_name` and `instance_name`.
- `pantechdynamics_database_engines`: new read-only `storage` on each engine, one entry per zone with `zone_id`, `min_gb`, `min_is_plan_disk`, `max_gb`, `step_gb`, `price_per_gb_month_minor` and `currency` (both null when unpriced): the limits and price for `storage_gb`.
- `pantechdynamics_regions` and `pantechdynamics_region`: new read-only `private_network_cidr` on each placement, the zone's private database network range (null where there is none, and always for `vpc`).
- A failed operation whose failure code is one of the `PROVISIONING_*` codes now adds what to do next (choose another plan or region, apply again later, delete unused resources, or contact support with the operation id).
- Database and instance orders that failed with `payment_expired` (not paid within one hour) or, for a database, `organization_deleted` (cancelled because the organization was deleted; any payment returned to credit) say so in the error.

BUG FIXES:

- A `422` error no longer lists every invalid field twice: the API now builds its `detail` from the field errors, so the provider prints the title and the field list instead.
- `pantechdynamics_database` descriptions now match the API's rules exactly: every reserved `admin_username`, `access_rules` host bits and the 1024-range limit shared with `security_group_ids`, `storage_gb`'s zone minimum, and the one-hour payment window.

- `pantechdynamics_public_ip`: `zone` was always empty, because the API field is `zone`, not `zone_id`.
- Firewall rules and port forwarding rules are read with their single-rule endpoints instead of searching the whole list, and every list (including plans, images, regions and disk offerings) now follows `next_cursor`, so a paginated list can no longer be cut short or fail.
- Rename, stop and resize of instances, resize and delete of volumes, and delete of snapshots are now retried on gateway errors with the same `Idempotency-Key`, which the API replays. SSH key create and delete still never retry, because the API does not replay them.
- Documentation, examples and errors now give the production base URL as `https://api.pantechdynamics.com/public/v1`, and a `GATEWAY_NO_ROUTE` error says to check the `/public/v1` prefix.
